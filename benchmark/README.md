# ClinLoop-Bench v1.0

An open benchmark for **closed-loop clinical follow-up tracking**: does a system notice that a report or
result creates a follow-up obligation, and can it tell, at a given time, whether that obligation was met?
It is built entirely from the synthetic blind-evaluation sets in this repository.

ClinLoop-Bench does not measure diagnosis. It measures the bookkeeping that prevents missed follow-up:
the recommended CT that never happened, the reactive screen that was never confirmed.

## Tasks

| Task | Input | Output | Records (dev / test) |
|---|---|---|---|
| **T1** Report → obligation (English) | one report text + patient context (also as a FHIR Bundle) | the catalogue rule ids the report obligates (`R003`, `R036`, …), optionally an evidence sentence per rule | 416 (130 / 286) |
| **T2** Timeline → loop status | a patient timeline or a FHIR record set + an evaluation time | for each obligation: `open` / `closed` / `needs_human_review`, and whether it is overdue | 317 (108 / 209) |
| **T3** Report → obligation (Korean & mixed) | as T1, Korean (51) or mixed Korean/English (223) reports | as T1 | 274 (78 / 196) |

T2 languages: 262 English, 51 mixed, 4 Korean. Total: **1,007 records**.

The rule catalogue (ids, names, guideline basis, default deadlines) is `tests/report_eval/rule_catalog.json`
for the report rules (R003–R046); T2 also uses the laboratory, colonoscopy and echocardiography rules
R060–R065 described in `docs/ACCURACY_EVALUATION.md`. Each record lists the rules it is scored on in
`gold.scope_rules`; predictions outside that scope are ignored, except non-catalogue labels, which always
count as false positives.

### Record schema (`schema.json`)

`id` (`<source>:<original id>`, stable), `version`, `task`, `language` (`en` / `ko` / `mixed`), `split`
(`dev` / `test`), `synthetic` (always `true`), `source` (file, evaluation round, original id), `input`
(`text`, `title`, `patient`, `events`, `fhir_bundle`, …), `eval_time`, `gold`:

- `rules`: obligated rule ids; `window_days`: expected deadline window [min, max] where the writer gave one;
- `obligations` (T2): `{rule: {status, overdue, deadline_days, source_label}}`. Timeline labels map
  `done → closed / not overdue`, `done_late → closed / overdue`, `pending → open / not overdue`,
  `missed → open / overdue`. For the FHIR record sets `overdue` is `null` (not labelled);
- `evidence_spans`: `null` in v1.0 (see limitations); the scorer uses them when a later version adds them;
- `scope_rules`.

**Split.** `dev` if `int(sha256("42:" + id)) % 100 < 30`, else `test`. It depends only on the id, so a
record keeps its split when later rounds are added. Tune on `dev`; report `test`.

## How to run

```bash
python scripts/build_benchmark.py                       # regenerate data (after every new evaluation round)
python benchmark/baselines/run_baselines.py             # baselines -> predictions/*.jsonl and RESULTS.md
python benchmark/score.py my_predictions.jsonl          # score the test split
python benchmark/score.py my_predictions.jsonl --split dev --json
python -m pytest -q tests/test_benchmark.py
```

Prediction format, one JSON object per line:

```json
{"id": "report_eval:C002", "rules": ["R003"], "evidence": {"R003": "Recommend CT in 12 months."}}
{"id": "timelines:T01", "obligations": {"R003": {"status": "open", "overdue": true}}}
```

Optional LLM baseline: set `CLINLOOP_OLLAMA_URL` (default `http://localhost:11434`) and optionally
`CLINLOOP_BENCH_OLLAMA_MODEL`. It is skipped when no server answers; no external API is ever called.

## Metrics

All are pooled (micro) over the records of a task and split, with **95% CIs from a 1,000-sample
bootstrap over records** (`numpy.random.default_rng(42)`).

- **Rule precision / recall / F1** — over (record, rule id) pairs, exact rule ids.
- **Finding F1** (T1, T3) — the same after mapping rule ids to *finding groups* (`manifest.json`
  `rule_groups`): a guideline rule and the radiologist's own recommendation for the same finding are one
  alert in ClinLoop, so either is accepted.
- **Needs-follow-up P / R / F1, specificity** (T1, T3) — report level: does the report obligate anything?
  This is the metric a rule-agnostic system (e.g. the keyword baseline) can be compared on.
- **Exact match** — the predicted rule set equals the gold set.
- **Evidence token F1** (T1, T3) — best token-level F1 between the predicted and gold evidence sentence per
  gold rule. Reported `n/a` in v1.0 (no gold spans).
- **Status accuracy** (T2) — per gold obligation, predicted status equals gold. A missing prediction is
  wrong. Matched by rule id, else by a predicted rule of the same finding group. `needs_human_review` is
  accepted for a gold `open` obligation (routing an unresolved loop to a person is a safe answer), and is
  also counted separately.
- **Overdue accuracy** (T2) — over gold obligations with a known `overdue` label (timelines only).
- **False closures** (T2) — gold `open`, predicted `closed`. The safety-critical error; report it.

## Data provenance

**All records are synthetic. None comes from a patient.** They were written for ClinLoop's blind
evaluations (`docs/ACCURACY_EVALUATION.md`):

- **Report sets** (`tests/report_eval/cases.json`, rounds `dev`, `heldout`, `confirm`, `real`, `confirm2`,
  `r8en`, `r8ko`, `r8confirm`): short impressions and full real-style reports with patient context. Writers
  acting as radiologists and pathologists saw **only the rule catalogue**, never ClinLoop's code, and gave
  the expected rules, deadline window and a rationale.
- **Timelines** (`tests/report_eval/timelines.json`): 60 patient histories with expected status per
  obligation.
- **FHIR record sets** (`tests/blind_reports_2`, `tests/blind_reports_3`): 157 + 100 cases written from the
  guideline definitions alone; the second in the style of real Korean hospital documents.

**Model-written caveat.** The case writers were language-model agents prompted to act as clinicians, not
practising clinicians, and the gold labels have not yet been adjudicated by a clinician panel. The texts
therefore carry model habits (phrasing, regular structure) and the labels carry the writers' reading of
the guidelines. Treat the benchmark as a software-verification benchmark, not clinical validation.

**Not included:** `tests/report_eval/second_reader/cases_*.json` (duplicates of rounds `real` and
`confirm2`); `second_reader/output_*.json` (model outputs, not labels); `src/clinloop_engine/data_generator.py`
trajectories (their labels come from the same rules being tested — circular); `demo/examples` and
`data/fhir_example_bundle.json` (no gold labels); `tests/hospital_eval` (not from a blind writer).

FHIR resources are exported without `name`, `identifier`, `telecom`, `address`, `photo` and `contact`
fields (one source set carried placeholder names such as "Synthetic Case001").

## Known limitations

- **Contamination of the reference system.** ClinLoop's rules were fixed after each round was scored once,
  so the rules-engine results in `RESULTS.md` are after-fix and optimistic. First-pass scores are in
  `docs/ACCURACY_EVALUATION.md`.
- **Synthetic, model-written text** (above); the long tail of real report wording is under-represented.
- **No gold evidence spans** in v1.0; no `needs_human_review` gold label; `overdue` labelled only for timelines.
- **Catalogue-bound labels.** Gold labels are ClinLoop rule ids; another system must map its output onto
  the catalogue (or use the needs-follow-up metric).
- **Small per-rule counts.** Many rules have under ten positives; per-rule metrics are noisy.
- **Single-site style.** Korean reports reflect one style of Korean hospital documentation.
- **Moving sources.** The source sets grow with each evaluation round; the benchmark is versioned, and
  `manifest.json` records the SHA-256 of each source. Re-run `scripts/build_benchmark.py` after a round and
  bump the version for a release; `tests/test_benchmark.py` flags stale data (`CLINLOOP_BENCH_STRICT=1`
  makes that a failure).
